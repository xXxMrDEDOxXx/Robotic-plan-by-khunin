## แขนง 4 การเขียนโปรแกรม C++ และ Python ระดับวิชาชีพ

> **ข้อสรุปของแขนงนี้:** เป้าหมายคือระดับใช้คล่อง (fluent) ใน C++17, C++20 และ Python ภายใน 31 มีนาคม 2571 (ปีที่ 2 ไตรมาส 2) ด้วยงบประมาณ 350 ชั่วโมง โดยต้องพร้อมสัมภาษณ์งานภายใน 31 สิงหาคม 2570 ตามเส้นทางวิกฤต สิ่งที่สำคัญที่สุดคือเขียนโค้ดที่ถูกต้องเรื่องอายุของทรัพยากรและการทำงานพร้อมกันจนผ่านเครื่องมือตรวจขณะรัน (sanitizer) ทุกครั้ง เพราะข้อผิดพลาดสองกลุ่มนี้ทำให้หุ่นยนต์ล่มแบบสุ่มและหาสาเหตุยาก

### (ก) หัวข้อหลัก หัวข้อย่อย และหัวข้อย่อยระดับลึก

- **1. พื้นฐาน C++ สมัยใหม่และโมเดลการคอมไพล์** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 1 ชั่วโมงประมาณ 45)
  - **1.1 คอมไพเลอร์ ลิงเกอร์ และวินัยเรื่องคำเตือน** ใช้กับโค้ดหุ่นยนต์ทุกชิ้นตั้งแต่โปรเจกต์ที่ 1
    - 1.1.1 อธิบายขั้นพรีโปรเซส คอมไพล์ และลิงก์ (preprocess, compile, link) และแยกข้อผิดพลาดของคอมไพเลอร์กับของลิงเกอร์ (linker) ได้
    - 1.1.2 คอมไพล์ด้วย `-std=c++20 -Wall -Wextra -Wpedantic -Werror` เป็นค่าเริ่มต้น และแก้คำเตือนแทนการปิดคำเตือน
    - 1.1.3 ใช้ดีบักเกอร์ (debugger) ตั้งจุดพัก ไล่ทีละบรรทัด และอ่าน call stack
  - **1.2 ชนิดข้อมูล การแปลงชนิด และพฤติกรรมที่มาตรฐานไม่ได้นิยาม** ต้นเหตุของบั๊กในการอ่านค่าเซนเซอร์และรีจิสเตอร์
    - 1.2.1 เลือก `std::int32_t`, `std::uint8_t` และ `double` ให้เหมาะกับข้อมูล และทำนายผลการล้น (overflow) ได้ถูก
    - 1.2.2 ใช้ `static_cast`, `const`, `constexpr` และ `auto` ถูกที่ และบอกได้ว่าการแปลงชนิดโดยนัย (implicit conversion) แบบใดทำให้ข้อมูลหาย
    - 1.2.3 ระบุพฤติกรรมที่มาตรฐานไม่ได้นิยาม (undefined behavior ย่อว่า UB คือโค้ดที่มาตรฐานไม่กำหนดผล) อย่างน้อย 5 แบบ และจับด้วย UndefinedBehaviorSanitizer
  - **1.3 การอ้างอิง ตัวชี้ และอายุของออบเจกต์** ส่งข้อมูลใหญ่ เช่น ภาพ โดยไม่คัดลอก
    - 1.3.1 เลือกส่งแบบค่า แบบอ้างอิงค่าคงที่ (const reference) หรือแบบตัวชี้ ตามขนาดข้อมูลและผู้เป็นเจ้าของ
    - 1.3.2 อธิบายขอบเขต (scope) และระยะเวลาการมีอยู่ (storage duration) และหาอ้างอิงห้อย (dangling reference การอ้างถึงออบเจกต์ที่ถูกทำลายแล้ว) ในโค้ดที่ไม่เคยเห็น
  - **1.4 คลาสและการแยกไฟล์** หน่วยพื้นฐานของไดรเวอร์และโมดูลหุ่นยนต์
    - 1.4.1 เขียนคลาสที่รักษาเงื่อนไขคงตัว (invariant เงื่อนไขที่ต้องจริงตลอดอายุออบเจกต์) และแยกไฟล์ส่วนหัวกับไฟล์ต้นฉบับตามกฎนิยามเดียว (one definition rule)
    - 1.4.2 ใช้ `std::vector`, `std::array` และ `std::string` แทนอาร์เรย์และสตริงแบบภาษา C ในโค้ดใหม่ทั้งหมด

- **2. คลาส RAII ความหมายของการย้าย และพหุสัณฐาน** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 2 ชั่วโมงประมาณ 50)
  - **2.1 RAII และกฎห้าข้อ** RAII (resource acquisition is initialization ผูกการจองและคืนทรัพยากรกับอายุออบเจกต์) ใช้กับหน่วยความจำ ไฟล์ พอร์ตอนุกรม และล็อก
    - 2.1.1 เขียนฟังก์ชันพิเศษครบตามกฎห้าข้อ (rule of five) และบอกได้ว่าเมื่อใดใช้กฎศูนย์ข้อ (rule of zero) แทน
    - 2.1.2 ห่อ file descriptor ของพอร์ตอนุกรมให้คืนครบแม้เกิดข้อยกเว้น
  - **2.2 ความหมายของการย้ายและ rvalue reference** การย้าย (move semantics) โอนทรัพยากรแทนการคัดลอก
    - 2.2.1 อธิบาย rvalue (ค่าชั่วคราวที่ย้ายทรัพยากรออกได้) และว่า `std::move` เป็นเพียงการแปลงชนิด
    - 2.2.2 วัดจำนวนการคัดลอกเมื่อ `std::vector` ขยายความจุ ทั้งแบบมีและไม่มี `noexcept`
    - 2.2.3 อธิบาย copy elision (คอมไพเลอร์ละการคัดลอก) ว่าทำไมการคืนออบเจกต์ใหญ่จากฟังก์ชันจึงไม่ช้า
  - **2.3 smart pointer และความเป็นเจ้าของ** ออบเจกต์ที่ห่อตัวชี้และคืนหน่วยความจำอัตโนมัติ ซึ่ง ROS 2 ใช้เกือบทุกที่
    - 2.3.1 ใช้ `std::unique_ptr` เป็นค่าเริ่มต้น ใช้ `std::shared_ptr` เมื่อมีเจ้าของร่วมจริง และ `std::weak_ptr` ตัดวงอ้างอิง
    - 2.3.2 อ่านลายเซ็นของฟังก์ชันแล้วบอกได้ว่าใครเป็นเจ้าของออบเจกต์
  - **2.4 การสืบทอดและฟังก์ชันเสมือน** พหุสัณฐานขณะรัน (runtime polymorphism) ใช้สลับไดรเวอร์ และเป็นรูปแบบของ hardware interface ใน ros2_control
    - 2.4.1 เขียนคลาสฐานแบบนามธรรมที่มี virtual destructor และใช้ `override` ทุกจุด
    - 2.4.2 อธิบายตารางฟังก์ชันเสมือน (vtable) ต้นทุนของการเรียกฟังก์ชันเสมือน และการตัดส่วนออบเจกต์ (object slicing)
  - **2.5 ความปลอดภัยต่อข้อยกเว้น** สถานะของระบบเมื่อเกิดข้อผิดพลาดกลางคำสั่ง
    - 2.5.1 บอกการรับประกันแบบพื้นฐาน แบบเข้ม และแบบไม่โยน และเขียน copy and swap
    - 2.5.2 เลือกระหว่างข้อยกเว้น รหัสข้อผิดพลาด และ `std::optional` สำหรับโค้ดในลูปควบคุม

- **3. Python ตามสำนวนของภาษา** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 3 ชั่วโมงประมาณ 50)
  - **3.1 โมเดลข้อมูลและโครงสร้างข้อมูลในตัว** เมธอดพิเศษ (special method) ทำให้คลาสที่เขียนเองใช้กับ `len` และ `for` ได้
    - 3.1.1 เขียนคลาสที่มี `__repr__`, `__eq__`, `__len__` และ `__iter__`
    - 3.1.2 เลือก list, tuple, dict, set และ deque ตามต้นทุนของการดำเนินการ
    - 3.1.3 อธิบายการคัดลอกตื้นกับคัดลอกลึก (shallow copy, deep copy) และกับดักของค่าเริ่มต้นที่เปลี่ยนแปลงได้
  - **3.2 ฟังก์ชันชั้นหนึ่ง closure และ decorator** ใช้สร้าง callback และตัวจับเวลา
    - 3.2.1 เขียน decorator (ฟังก์ชันที่ครอบฟังก์ชันอื่นเพื่อเพิ่มพฤติกรรม) จับเวลาโดยใช้ `functools.wraps`
    - 3.2.2 อธิบาย closure (ฟังก์ชันที่จำตัวแปรจากขอบเขตที่สร้างมัน) และใช้ `nonlocal` ถูก
  - **3.3 generator และ context manager** อ่าน log ขนาดใหญ่ทีละบรรทัด และเปิดปิดอุปกรณ์อย่างปลอดภัย
    - 3.3.1 เขียน generator อ่าน CSV 1,000,000 บรรทัดด้วยหน่วยความจำไม่เกิน 50 เมกะไบต์
    - 3.3.2 เขียน context manager แบบคลาสและแบบ `contextlib.contextmanager`
  - **3.4 dataclass, Protocol และคำบอกใบ้ชนิดข้อมูล** คำบอกใบ้ชนิดข้อมูล (type hints) ให้เครื่องมือหาบั๊กก่อนรัน
    - 3.4.1 สร้าง dataclass (คลาสเก็บข้อมูลที่สร้างเมธอดพื้นฐานให้เอง) แบบ frozen สำหรับท่าทาง (pose) และข้อความเซนเซอร์
    - 3.4.2 ใช้ `typing.Protocol` (ส่วนต่อประสานแบบโครงสร้าง ไม่ต้องสืบทอด) และผ่าน `mypy --strict` กับ ruff
  - **3.5 การทำงานพร้อมกันใน Python** GIL (global interpreter lock ล็อกที่ให้ CPython รันไบต์โค้ดได้ทีละเธรด) กำหนดว่าใช้เธรด โปรเซส หรือ asyncio
    - 3.5.1 เลือก `threading`, `multiprocessing` หรือ `asyncio` ตามว่างานติดที่ I/O หรือ CPU
    - 3.5.2 อธิบายผลของรุ่นที่ปิด GIL ได้ (ข้อเสนอ PEP 703 เริ่มแบบทดลองใน Python 3.13) และทำไมยังต้องใช้ล็อก

- **4. Template, STL และ C++20** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 4 ชั่วโมงประมาณ 60)
  - **4.1 function template และ class template** โค้ดที่คอมไพเลอร์สร้างใหม่ตามชนิดข้อมูล
    - 4.1.1 เขียน `RingBuffer<T, N>` ที่มีพารามิเตอร์ชนิดและพารามิเตอร์ค่า
    - 4.1.2 อ่านข้อความผิดพลาดยาวของ template จนหาบรรทัดต้นเหตุได้
  - **4.2 container และ iterator** โครงสร้างเก็บข้อมูลและตัวไล่สมาชิกของไลบรารีแม่แบบมาตรฐาน (Standard Template Library ย่อว่า STL) ที่ควรใช้แทนการเขียนเอง
    - 4.2.1 เลือก container จากความซับซ้อนและ cache locality (การวางข้อมูลติดกันที่ทำให้ CPU อ่านเร็ว)
    - 4.2.2 บอกกฎ iterator invalidation (iterator ใช้ไม่ได้หลังแก้ container) และหาบั๊กจากกฎนี้
    - 4.2.3 เขียน iterator ให้ container ที่สร้างเองใช้กับอัลกอริทึมมาตรฐานได้
  - **4.3 อัลกอริทึมมาตรฐาน lambda และ ranges** แทนลูปเขียนเองด้วยฟังก์ชันที่บอกเจตนา
    - 4.3.1 ใช้ `std::sort`, `std::partition`, `std::transform` และ `std::lower_bound` พร้อมบอกความซับซ้อน
    - 4.3.2 เขียน lambda (ฟังก์ชันไม่มีชื่อ) ที่จับตัวแปรถูกแบบ และชี้ได้ว่าการจับแบบใดทำให้เกิดอ้างอิงห้อย
    - 4.3.3 ใช้ `std::ranges` และ views ของ C++20 กับข้อมูลเซนเซอร์
  - **4.4 ชนิดข้อมูลสำหรับค่าที่อาจไม่มีและค่าหลายรูปแบบ** แทนค่าพิเศษและตัวชี้ว่าง
    - 4.4.1 ใช้ `std::optional` แทนค่าลบหนึ่งเมื่อเซนเซอร์ไม่มีข้อมูล
    - 4.4.2 ใช้ `std::variant` กับ `std::visit` สร้างเครื่องสถานะ (state machine) ของโหมดหุ่นยนต์
    - 4.4.3 ใช้ `std::span` และ `std::string_view` ส่งข้อมูลโดยไม่คัดลอก
  - **4.5 concept, constexpr และโค้ดแบบสัมภาษณ์** ส่วนที่บริษัทใช้คัดคนในรอบเขียนโค้ด
    - 4.5.1 เขียน concept (เงื่อนไขของชนิดข้อมูลใน C++20) จำกัดพารามิเตอร์ของ template
    - 4.5.2 ใช้ `constexpr` สร้างตารางค่าคงที่ตอนคอมไพล์ เช่น ตารางค่าไซน์
    - 4.5.3 แก้โจทย์ระดับกลางด้วย STL และด้วย Python ใน 30 ถึง 45 นาทีต่อข้อ พร้อมอธิบายความซับซ้อนออกเสียง (ใช้ร่วมกับแขนง 3)

- **5. แพ็กเกจ การทดสอบ และ NumPy** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 2 ไตรมาส 1 ชั่วโมงประมาณ 40)
  - **5.1 แพ็กเกจและ pyproject.toml** ทำให้โค้ดติดตั้งซ้ำได้บนเครื่องใหม่และบนหุ่นยนต์
    - 5.1.1 สร้างแพ็กเกจแบบ src layout ที่ติดตั้งใน environment ใหม่ด้วย `pip install -e .` ได้ในครั้งแรก
    - 5.1.2 ใช้ virtual environment (ชุดแพ็กเกจแยกต่อโปรเจกต์) และอธิบายว่าทำไม Ubuntu รุ่นใหม่ห้ามติดตั้งลง Python ของระบบ (PEP 668)
  - **5.2 pytest กับโค้ดตัวเลข** การทดสอบอัตโนมัติสำหรับโค้ดที่ผิดได้แบบเงียบ ๆ
    - 5.2.1 เขียน fixture (ข้อมูลตั้งต้นที่ใช้ซ้ำ) และ parametrize ครอบคลุมกรณีขอบ เช่น อาร์เรย์ว่างและค่า NaN
    - 5.2.2 เทียบเลขทศนิยมด้วย `pytest.approx` หรือ `np.allclose` พร้อมเหตุผลของค่าความคลาดเคลื่อน
    - 5.2.3 วัดความครอบคลุมของโค้ด (code coverage) ด้วย pytest-cov
  - **5.3 NumPy และการคำนวณแบบเวกเตอร์** การคำนวณแบบเวกเตอร์ (vectorization) คือสั่งงานทั้งอาร์เรย์ในคำสั่งเดียวแทนลูปของ Python
    - 5.3.1 อธิบาย dtype, shape, stride และความต่างระหว่าง view กับ copy
    - 5.3.2 ใช้ broadcasting (การขยายมิติอัตโนมัติ) แปลงพิกัดจุด 100,000 จุดในคำสั่งเดียว
    - 5.3.3 วัดด้วย timeit จนแบบเวกเตอร์เร็วกว่าแบบลูปอย่างน้อย 20 เท่า
  - **5.4 การวิเคราะห์ log ของหุ่นยนต์** หาสาเหตุจากข้อมูลที่บันทึกไว้หลังหุ่นยนต์ทำงานผิด
    - 5.4.1 เทียบเวลาข้อมูลสองเซนเซอร์ที่อัตราต่างกันด้วยการประมาณค่าในช่วง (interpolation)
    - 5.4.2 วาดกราฟด้วย Matplotlib ที่มีชื่อแกนและหน่วยครบ

- **6. การทำงานพร้อมกันและลูปเวลาจริงใน C++** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 2 ไตรมาส 1 ชั่วโมงประมาณ 50)
  - **6.1 เธรด mutex และ condition variable** หุ่นยนต์อ่านเซนเซอร์ ควบคุม และสื่อสารพร้อมกัน
    - 6.1.1 ใช้ `std::jthread` และหยุดอย่างเรียบร้อยด้วย `std::stop_token`
    - 6.1.2 เขียนคิวมีขอบเขตด้วย `std::mutex` และ `std::condition_variable` ที่รับมือการตื่นโดยไม่มีสัญญาณ (spurious wakeup)
    - 6.1.3 หาและแก้การติดตาย (deadlock)
  - **6.2 atomic และโมเดลหน่วยความจำ** กติกาว่าเธรดหนึ่งเห็นการเขียนของอีกเธรดเมื่อใด
    - 6.2.1 อธิบายว่าการแย่งข้อมูล (data race) เป็น UB และจับด้วย ThreadSanitizer
    - 6.2.2 ใช้ memory order แบบ relaxed, acquire และ release และอธิบายว่าทำไมคู่ acquire กับ release พอสำหรับคิวผู้ผลิตหนึ่งผู้บริโภคหนึ่ง
    - 6.2.3 เขียนบัฟเฟอร์วงแหวนแบบไม่ใช้ล็อก (lock-free) และแก้การแชร์ cache line โดยไม่ตั้งใจ (false sharing)
  - **6.3 ลูปเวลาจริง** ลูปควบคุมต้องทำงานตรงคาบ ถ้าช้าหุ่นยนต์อาจสั่นหรือล้ม
    - 6.3.1 เขียนลูป 1 กิโลเฮิรตซ์ด้วย `std::chrono::steady_clock` และวัดความไม่สม่ำเสมอของคาบ (jitter) ที่เปอร์เซ็นไทล์ที่ 99
    - 6.3.2 ย้ายการจองหน่วยความจำ ล็อก และ I/O ออกจากลูป และพิสูจน์ด้วยตัวนับ operator new
    - 6.3.3 อธิบายว่าทำไมลินุกซ์ทั่วไปไม่รับประกันเวลา (เคอร์เนลเวลาจริงอยู่ในแขนง 18)
  - **6.4 งานอะซิงโครนัสและพูลเธรด** กระจายงานคำนวณหนักโดยไม่สร้างเธรดใหม่ทุกครั้ง
    - 6.4.1 ใช้ `std::async` และ `std::future` และบอกข้อจำกัด
    - 6.4.2 เขียนพูลเธรด (thread pool) ที่ปิดตัวได้โดยไม่ทิ้งงานค้าง

- **7. Eigen ประสิทธิภาพ และการเชื่อม C++ กับ Python** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 2 ไตรมาส 2 ชั่วโมงประมาณ 55 รวมงานปิดแขนงประมาณ 30)
  - **7.1 Eigen** ไลบรารีเมทริกซ์ที่ไลบรารีหุ่นยนต์ด้าน C++ จำนวนมากใช้
    - 7.1.1 เลือกเมทริกซ์ขนาดคงที่หรือขนาดเปลี่ยนได้ และใช้ `Eigen::Quaternion` กับ `Eigen::Isometry3d`
    - 7.1.2 แก้ระบบสมการด้วยการแยกตัวประกอบที่เหมาะกับเมทริกซ์ เช่น LDLT และ QR
    - 7.1.3 หลีกเลี่ยงกับดักของ expression template (นิพจน์ที่ยังไม่คำนวณจนกว่าจะกำหนดค่า) และ aliasing (ผลลัพธ์เขียนทับข้อมูลต้นทาง)
  - **7.2 การวัดและปรับประสิทธิภาพ** วัดก่อนแก้ทุกครั้ง
    - 7.2.1 เขียน micro-benchmark (การวัดเวลาโค้ดชิ้นเล็ก) ที่กันคอมไพเลอร์ตัดโค้ดทิ้ง และเทียบ `-O0` กับ `-O2`
    - 7.2.2 เทียบอาร์เรย์ของโครงสร้างกับโครงสร้างของอาร์เรย์ (array of structures, structure of arrays) ด้วยตัวเลขที่วัดได้
    - 7.2.3 ใช้ Compiler Explorer ยืนยันว่าคอมไพเลอร์ inline หรือ vectorize หรือไม่ (perf และ flame graph อยู่ในแขนง 5)
  - **7.3 binding ด้วย pybind11** ห่อโค้ด C++ ให้เรียกและทดสอบจาก Python ได้
    - 7.3.1 สร้างโมดูลจากคลาส C++ และ build ผ่าน CMake จนติดตั้งด้วย pip ได้
    - 7.3.2 รับอาร์เรย์ NumPy โดยไม่คัดลอก และปล่อย GIL ระหว่างคำนวณหนัก
    - 7.3.3 ทดสอบโมดูลด้วย pytest โดยใช้ NumPy เป็นคำตอบอ้างอิง
  - **7.4 ระบบขนาดกลางที่ผสมสองภาษา** งานทดสอบปิดแขนงที่รวมหัวข้อ 1 ถึง 7
    - 7.4.1 แบ่งงานระหว่าง C++ (ลูปเวลาจริง) กับ Python (วิเคราะห์และทดสอบ) พร้อมเหตุผลจากผลวัดเวลา
    - 7.4.2 เขียนรายงานการออกแบบ 2 ถึง 4 หน้า แล้วแก้ทุกประเด็นจากผู้ตรวจภายนอกจนไม่มีประเด็นค้าง

## แขนง 5 วิศวกรรมซอฟต์แวร์

> **ข้อสรุปของแขนงนี้:** แขนงนี้ต้องถึงระดับใช้คล่องภายใน 30 กันยายน 2571 (ปีที่ 2) ด้วยชั่วโมงรวมประมาณ 150 ชั่วโมง โดยเริ่มนิสัย Git ทุกวันตั้งแต่ปีที่ 1 ไตรมาส 1 สิ่งที่สำคัญที่สุดคือทุกโปรเจกต์ของแผนต้องมี repository ที่คนอื่น clone แล้ว build ทดสอบ และรันได้จาก README อย่างเดียว เพราะนายจ้างและผู้ร่วมโอเพนซอร์สตัดสินฝีมือจากสิ่งนี้ก่อนอ่านโค้ด

### (ก) หัวข้อหลัก หัวข้อย่อย และหัวข้อย่อยระดับลึก

วิศวกรรมซอฟต์แวร์ (software engineering) ในแขนงนี้หมายถึงชุดเครื่องมือและวิธีทำงานที่ทำให้โค้ดหุ่นยนต์ถูกต้อง ทำซ้ำได้ และทำงานร่วมกับคนอื่นได้ ไม่ได้หมายถึงการออกแบบสถาปัตยกรรมระบบใหญ่ ซึ่งอยู่ในแขนง 21

- **1. Git และโมเดลข้อมูลของการควบคุมเวอร์ชัน** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 1 ชั่วโมงประมาณ 25)
  - **1.1 โมเดลข้อมูลของ Git (data model)** Git เก็บประวัติเป็นกราฟของ commit ที่ชี้ไปยัง tree และ blob ซึ่งระบุด้วยค่าแฮช (hash) การเข้าใจโมเดลนี้ทำให้กู้งานคืนได้แทนการลบโฟลเดอร์แล้ว clone ใหม่
    - 1.1.1 อธิบายจากความจำว่า blob, tree, commit และ ref ต่างกันอย่างไร และวาดกราฟของ repository ขนาด 5 commit ด้วยมือให้ตรงกับผลของ `git log --graph --all`
    - 1.1.2 อธิบายว่า branch และ HEAD เป็นเพียงตัวชี้ (pointer) ไปยัง commit และสาธิตสถานะ detached HEAD แล้วออกจากสถานะนั้นโดยไม่เสีย commit
    - 1.1.3 ใช้ `git cat-file -p` เปิดดูวัตถุภายใน `.git` เพื่อยืนยันคำอธิบายของตนเอง
  - **1.2 วงจรการทำงานประจำวัน** พื้นที่ทำงาน (working tree) พื้นที่เตรียม (staging area หรือ index) และ repository เป็น 3 ที่ที่โค้ดอยู่ได้ ความสับสนระหว่าง 3 ที่นี้เป็นต้นเหตุของงานหายที่พบบ่อยที่สุด
    - 1.2.1 ใช้ `git add -p` แยกการเปลี่ยนแปลงในไฟล์เดียวออกเป็นหลาย commit ที่แต่ละ commit ทำเรื่องเดียว
    - 1.2.2 เขียนข้อความ commit ที่มีบรรทัดสรุปไม่เกิน 50 ตัวอักษรและเนื้อความบอกเหตุผล ไม่ใช่บอกเพียงว่าแก้อะไร
    - 1.2.3 ตั้ง `.gitignore` ที่ไม่เก็บไฟล์ build ไฟล์ข้อมูลขนาดใหญ่ และไฟล์ที่มีรหัสลับ (secret)
  - **1.3 branch, merge และ rebase** branch แยกงานแต่ละเรื่องออกจากกัน merge รวมประวัติไว้ทั้งหมด ส่วน rebase เขียนประวัติใหม่ให้เป็นเส้นตรง
    - 1.3.1 อธิบายความต่างระหว่าง fast-forward merge, merge commit และ rebase พร้อมบอกว่าเมื่อใดห้าม rebase (เมื่อ branch ถูกแชร์ให้คนอื่นแล้ว)
    - 1.3.2 แก้ข้อขัดแย้งในการรวมโค้ด (merge conflict) ทั้งแบบแก้ในไฟล์และแบบเลือกฝั่ง แล้วยืนยันด้วยการ build และทดสอบก่อน commit
    - 1.3.3 ใช้ interactive rebase รวม แก้ และเรียง commit ใน branch ของตนก่อนเปิดคำขอรวมโค้ด
  - **1.4 การกู้คืนและการสืบสวนประวัติ** งานจริงมักต้องย้อนหาว่าบั๊กเข้ามาเมื่อใด และต้องกู้งานที่คิดว่าหายไปแล้ว
    - 1.4.1 กู้ branch ที่ถูกลบหรือ commit ที่ reset ทิ้งด้วย `git reflog`
    - 1.4.2 ใช้ `git revert` ยกเลิก commit ที่เผยแพร่แล้วโดยไม่เขียนประวัติใหม่ และอธิบายว่าทำไมไม่ใช้ `git reset --hard` กับ branch ที่แชร์แล้ว
    - 1.4.3 ใช้ `git bisect` หา commit ที่ทำให้การทดสอบล้ม และใช้ `git blame` กับ `git log -S` หาที่มาของบรรทัดโค้ด
- **2. การทำงานร่วมกันบน GitHub และเอกสารโครงการ** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 2 ชั่วโมงประมาณ 20)
  - **2.1 remote และ fork** remote คือสำเนาของ repository บนเครื่องอื่น การทำงานกับโอเพนซอร์สใช้รูปแบบ fork คือสำเนาของตนเองบน GitHub ที่ส่งงานกลับไปยังต้นฉบับ (upstream)
    - 2.1.1 ตั้งค่าคีย์ SSH และใช้ `git fetch`, `git pull --rebase` และ `git push` กับ remote 2 ตัว (origin และ upstream) ได้ถูกต้อง
    - 2.1.2 อัปเดต fork ให้ตรงกับ upstream โดยไม่สร้าง merge commit ที่ไม่จำเป็น และใช้ `git push --force-with-lease` เฉพาะกับ branch ของตนเอง
  - **2.2 issue และการวางแผนงาน** issue คือรายการปัญหาหรืองานที่บันทึกใน repository ใช้เป็นบันทึกการตัดสินใจและรายการงานของโปรเจกต์หุ่นยนต์
    - 2.2.1 เขียน issue รายงานบั๊กที่มีขั้นตอนทำซ้ำ ผลที่คาด ผลที่เกิดจริง และสภาพแวดล้อม (รุ่นระบบปฏิบัติการ คอมไพเลอร์ และฮาร์ดแวร์)
    - 2.2.2 ใช้ label, milestone และแม่แบบ issue (issue template) จัดงานของโปรเจกต์ที่ 1 และ 2 เป็นรายสัปดาห์
    - 2.2.3 เชื่อม commit และคำขอรวมโค้ดเข้ากับ issue ด้วยคำสั่งปิดอัตโนมัติ เช่น `Fixes #12`
  - **2.3 คำขอรวมโค้ด (pull request) และการรีวิวโค้ด (code review)** pull request คือการเสนอให้รวม branch หนึ่งเข้าอีก branch หนึ่งพร้อมพื้นที่ให้ผู้อื่นรีวิวทีละบรรทัด เป็นด่านคุณภาพหลักของทีมซอฟต์แวร์ทุกทีม
    - 2.3.1 เปิด pull request ขนาดไม่เกินประมาณ 400 บรรทัดที่เปลี่ยน พร้อมคำอธิบายว่าทำอะไร ทำไม และทดสอบอย่างไร
    - 2.3.2 รีวิว pull request ของผู้อื่นโดยแยกความเห็นที่ต้องแก้ ความเห็นที่เป็นคำถาม และความเห็นเรื่องรสนิยม และให้ข้อเสนอแนะที่ทำตามได้จริง
    - 2.3.3 ตอบรีวิวด้วย commit แก้ไขที่ตรวจตามได้ และตั้งกฎป้องกัน branch (branch protection) ให้ main ต้องผ่านการรีวิวก่อน merge
  - **2.4 README และเอกสารโครงการ (project documentation)** README คือหน้าแรกที่คนเห็น ส่วนเอกสารโครงการรวมถึงคู่มือการร่วมพัฒนา สัญญาอนุญาต (license) และบันทึกการเปลี่ยนแปลง (changelog)
    - 2.4.1 เขียน README ที่มีภาพหรือวิดีโอผลลัพธ์ ฮาร์ดแวร์ที่ใช้ คำสั่งติดตั้ง build ทดสอบ และรัน ซึ่งคนที่ไม่เคยเห็นโปรเจกต์ทำตามได้ภายใน 15 นาที
    - 2.4.2 เลือกสัญญาอนุญาต เช่น MIT, BSD-3-Clause หรือ Apache-2.0 และอธิบายผลต่อการนำไปใช้เชิงพาณิชย์
    - 2.4.3 เขียน CONTRIBUTING.md, CHANGELOG.md และบันทึกการตัดสินใจเชิงออกแบบ (architecture decision record) สั้น ๆ ไว้ในโฟลเดอร์ `docs/`
  - **2.5 รุ่นที่เผยแพร่ (release) และการกำหนดเลขรุ่น** release คือภาพนิ่งของโค้ดที่ผู้อื่นอ้างอิงได้
    - 2.5.1 ใช้ annotated tag และกำหนดเลขรุ่นแบบ semantic versioning (MAJOR.MINOR.PATCH) ให้สื่อว่ารุ่นใดเปลี่ยนส่วนต่อประสาน
    - 2.5.2 สร้าง GitHub Release พร้อมบันทึกประจำรุ่นที่อ้างถึง pull request ที่รวมเข้ามา
- **3. ระบบ build ด้วย CMake** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 3 ชั่วโมงประมาณ 25)
  - **3.1 แนวคิดของระบบ build (build system)** ระบบ build แปลงซอร์สโค้ดเป็นไลบรารีและโปรแกรมตามลำดับการพึ่งพา CMake เป็นตัวสร้างไฟล์ build (build system generator) ที่ ROS 2 และไลบรารี C++ ด้านหุ่นยนต์ส่วนใหญ่ใช้
    - 3.1.1 อธิบายขั้นตอนพรีโพรเซส คอมไพล์ และลิงก์ และอ่านข้อความผิดพลาดของตัวลิงก์ (linker) เช่น undefined reference ได้ว่าเกิดจากขั้นใด
    - 3.1.2 แยกขั้น configure กับขั้น build ของ CMake และ build นอกโฟลเดอร์ซอร์ส (out-of-source build) เสมอ
    - 3.1.3 เลือกประเภทการ build (Debug, Release, RelWithDebInfo) และอธิบายผลต่อการดีบักและความเร็ว
  - **3.2 CMake แบบเน้นเป้าหมาย (target-based CMake)** ทุกไลบรารีและโปรแกรมเป็นเป้าหมาย (target) ที่ประกาศความต้องการของตนเอง เช่น พาธ include และแฟล็กคอมไพเลอร์ แทนการตั้งค่ารวมทั้งโปรเจกต์
    - 3.2.1 ใช้ `add_library`, `add_executable` และ `target_link_libraries` กับคำว่า PUBLIC, PRIVATE และ INTERFACE ให้ถูกต้อง และอธิบายว่าความต้องการส่งต่อไปยังเป้าหมายที่ลิงก์อย่างไร
    - 3.2.2 ตั้งมาตรฐานภาษาและคำเตือนของคอมไพเลอร์ต่อเป้าหมาย เช่น `target_compile_features` และ `target_compile_options` โดยไม่ใช้ `include_directories` แบบรวม
    - 3.2.3 แบ่งโปรเจกต์เป็นโฟลเดอร์ย่อยด้วย `add_subdirectory` ให้แต่ละไลบรารีมีไฟล์ CMakeLists.txt ของตนเอง
  - **3.3 การจัดการไลบรารีภายนอก (dependency)** โค้ดหุ่นยนต์พึ่ง Eigen, GoogleTest และไลบรารีอื่นเสมอ การดึงไลบรารีให้ทำซ้ำได้คือหัวใจของการที่คนอื่น build ได้
    - 3.3.1 ใช้ `find_package` กับไลบรารีที่ติดตั้งในระบบ เช่น Eigen และอธิบายว่า CMake หาไฟล์ config ของแพ็กเกจจากที่ใด
    - 3.3.2 ใช้ `FetchContent` ดึง GoogleTest ในรุ่นที่ระบุแน่นอน และอธิบายข้อดีข้อเสียเทียบกับการติดตั้งในระบบ
  - **3.4 preset การติดตั้ง และการส่งออกแพ็กเกจ** preset คือไฟล์ CMakePresets.json ที่เก็บชุดค่าการ build ให้ทุกเครื่องใช้เหมือนกัน
    - 3.4.1 เขียน CMakePresets.json ที่มี preset สำหรับ Debug พร้อม sanitizer และ Release และใช้ preset เดียวกันในเครื่องตนเองและใน CI
    - 3.4.2 ใช้ `install` และส่งออกเป้าหมาย (export) ให้โปรเจกต์อื่นเรียก `find_package` หาไลบรารีของตนได้
    - 3.4.3 ส่งออก `compile_commands.json` ให้ตัวช่วยแก้ไขโค้ดและเครื่องมือวิเคราะห์ เช่น clangd และ clang-tidy ใช้ได้
- **4. การทดสอบอัตโนมัติด้วย GoogleTest และ pytest** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 3 ชั่วโมงประมาณ 25)
  - **4.1 หลักการทดสอบ** การทดสอบหน่วย (unit test) ตรวจฟังก์ชันหรือคลาสเดียว การทดสอบการรวม (integration test) ตรวจหลายส่วนทำงานร่วมกัน ในหุ่นยนต์ การทดสอบช่วยให้แก้ตัวควบคุมหรือตัวกรองได้โดยไม่ทำให้ส่วนอื่นพัง
    - 4.1.1 แยกโค้ดคำนวณออกจากโค้ดที่คุยกับฮาร์ดแวร์ เพื่อให้ทดสอบตัวควบคุม PID หรือการแปลงหน่วยของเซนเซอร์บนคอมพิวเตอร์ได้โดยไม่มีบอร์ด
    - 4.1.2 เลือกกรณีทดสอบจากค่าขอบ (boundary value) ค่าผิดปกติ และค่าที่ทำให้คำนวณเลขทศนิยมผิดพลาด แทนการเลือกค่าที่สะดวก
    - 4.1.3 เปรียบเทียบเลขทศนิยมด้วยค่าคลาดเคลื่อนที่ยอมรับได้ (tolerance) และอธิบายว่าทำไมห้ามเทียบด้วยเครื่องหมายเท่ากับ
  - **4.2 GoogleTest และ CTest** GoogleTest เป็นกรอบการทดสอบ (testing framework) ของ C++ ส่วน CTest เป็นตัวรันการทดสอบของ CMake
    - 4.2.1 เขียน `TEST`, `TEST_F` ที่ใช้ fixture และการทดสอบแบบกำหนดพารามิเตอร์ (parameterized test) ด้วย `TEST_P`
    - 4.2.2 ลงทะเบียนการทดสอบด้วย `gtest_discover_tests` แล้วรันด้วย `ctest --output-on-failure` และรันเฉพาะกรณีที่ล้ม
    - 4.2.3 ใช้วัตถุจำลอง (mock) ของ gMock แทนไดรเวอร์ฮาร์ดแวร์ เพื่อทดสอบตรรกะที่เรียกฮาร์ดแวร์
  - **4.3 pytest** กรอบการทดสอบของ Python ที่ใช้กับสคริปต์วิเคราะห์ข้อมูล โหนด ROS 2 ที่เขียนด้วย Python และโค้ดแขนง 19
    - 4.3.1 เขียน fixture, `pytest.mark.parametrize` และทดสอบว่าฟังก์ชันโยนข้อผิดพลาดที่ถูกต้องด้วย `pytest.raises`
    - 4.3.2 ใช้ `numpy.testing` เทียบอาร์เรย์ด้วยค่าคลาดเคลื่อน และใช้ `tmp_path` ทดสอบโค้ดที่อ่านเขียนไฟล์
  - **4.4 ความครอบคลุมของโค้ด (code coverage) และคุณภาพของการทดสอบ** ความครอบคลุมบอกว่าบรรทัดใดถูกรันระหว่างทดสอบ แต่ไม่ได้บอกว่าการทดสอบตรวจผลถูกหรือไม่
    - 4.4.1 วัดความครอบคลุมของ C++ ด้วย gcov หรือ llvm-cov และของ Python ด้วย pytest-cov แล้วอ่านรายงานหาเส้นทางที่ไม่เคยถูกทดสอบ
    - 4.4.2 วัดคุณภาพการทดสอบด้วยบั๊กจงใจ (ให้ผู้อื่นซ่อนบั๊กแล้วนับว่าการทดสอบจับได้กี่ตัว) ตามแนวคิดของการทดสอบแบบกลายพันธุ์ (mutation testing)
    - 4.4.3 เขียนการทดสอบที่ทำซ้ำบั๊กก่อนแก้ทุกครั้ง (regression test) เพื่อไม่ให้บั๊กเดิมกลับมา
- **5. การดีบักและการวัดประสิทธิภาพ** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 4 ชั่วโมงประมาณ 30)
  - **5.1 วิธีดีบักอย่างเป็นระบบ** การดีบัก (debugging) คือการหาสาเหตุของพฤติกรรมผิดด้วยการตั้งสมมติฐานและทดสอบ ไม่ใช่การแก้แบบสุ่ม
    - 5.1.1 ทำให้บั๊กเกิดซ้ำได้ด้วยตัวอย่างเล็กที่สุด (minimal reproducible example) ก่อนแก้ทุกครั้ง
    - 5.1.2 ใช้การบันทึกเหตุการณ์ (logging) แบบมีระดับความรุนแรงและเวลาประทับ แทนการใส่ `printf` แล้วลบทิ้ง
    - 5.1.3 บันทึกสมมติฐาน การทดลอง และผลไว้ใน issue เพื่อให้คนอื่นตรวจตามได้
  - **5.2 ดีบักเกอร์ gdb** ดีบักเกอร์ (debugger) หยุดโปรแกรมเพื่อดูค่าตัวแปรและลำดับการเรียกฟังก์ชัน
    - 5.2.1 ใช้ breakpoint, watchpoint, `backtrace`, `frame` และ `print` หาบรรทัดที่เกิดความผิดพลาดการแบ่งส่วนหน่วยความจำ (segmentation fault)
    - 5.2.2 เปิดไฟล์ core dump ของโปรแกรมที่ล้มไปแล้ว และดีบักโปรแกรมที่มีหลายเธรดด้วย `thread apply all bt`
    - 5.2.3 ใช้ `strace` ดูการเรียกระบบ (system call) เมื่อโปรแกรมค้างหรือเปิดอุปกรณ์ เช่น พอร์ตอนุกรม ไม่ได้
  - **5.3 sanitizer และ Valgrind** sanitizer คือเครื่องมือที่คอมไพเลอร์แทรกเข้าไปในโปรแกรมเพื่อจับความผิดพลาดของหน่วยความจำและเธรดขณะรัน
    - 5.3.1 จับการใช้หน่วยความจำที่คืนแล้ว (use-after-free) และการเขียนเกินขอบอาร์เรย์ด้วย AddressSanitizer และจับพฤติกรรมที่ไม่นิยาม (undefined behavior) ด้วย UndefinedBehaviorSanitizer
    - 5.3.2 จับการแย่งข้อมูลระหว่างเธรด (data race) ด้วย ThreadSanitizer และอ่านรายงานจนชี้ตัวแปรและเธรดที่ขัดกันได้
    - 5.3.3 ใช้ Valgrind Memcheck กับโปรแกรมที่คอมไพล์ใหม่ไม่ได้ และอธิบายว่าทำไมช้ากว่า sanitizer มาก
  - **5.4 การวัดประสิทธิภาพ (profiling)** profiling คือการวัดว่าเวลาและหน่วยความจำถูกใช้ที่ใด เพื่อให้วงควบคุมและการประมวลผลภาพทันคาบเวลา
    - 5.4.1 วัดเวลาแบบมีสถิติด้วย hyperfine โดยรันซ้ำอย่างน้อย 10 รอบและรายงานค่าเฉลี่ยกับส่วนเบี่ยงเบนมาตรฐาน
    - 5.4.2 สุ่มตัวอย่างด้วย `perf record` แล้วสร้างกราฟเปลวไฟ (flame graph) หาฟังก์ชันที่ใช้เวลามากที่สุด
    - 5.4.3 วัดโค้ด Python ด้วย cProfile หรือ py-spy และตัดสินว่าควรย้ายส่วนใดไป NumPy หรือ C++
    - 5.4.4 วัดความหน่วงสูงสุด (worst-case latency) ของลูปที่ต้องทันเวลา ไม่ใช่เฉพาะค่าเฉลี่ย เพราะวงควบคุมพังจากรอบที่ช้าที่สุด
- **6. การรวมโค้ดอย่างต่อเนื่อง (continuous integration หรือ CI) และ Docker** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 2 ไตรมาส 1 ชั่วโมงประมาณ 25)
  - **6.1 GitHub Actions** CI คือการให้เครื่องอื่น build และทดสอบทุก commit และทุก pull request โดยอัตโนมัติ GitHub Actions เป็นบริการ CI ที่ฝังใน GitHub
    - 6.1.1 อ่านและเขียนไฟล์ workflow ในรูปแบบ YAML ที่มี trigger, job และ step และอธิบายว่า job แต่ละตัวรันบนเครื่องใหม่ที่ว่างเปล่า
    - 6.1.2 ใช้ matrix รัน build บน GCC และ Clang และรัน pytest บน Python 2 รุ่นในการตั้งค่าเดียว
    - 6.1.3 ใช้แคช (cache) ของไลบรารีและผล build ให้ workflow เสร็จภายใน 10 นาที และอธิบายว่าคีย์ของแคชควรขึ้นกับไฟล์ใด
  - **6.2 ด่านคุณภาพอัตโนมัติ (quality gate)** คือการตรวจที่ต้องผ่านก่อน merge เพื่อไม่ให้ main พัง
    - 6.2.1 เพิ่ม job ที่ build ด้วย AddressSanitizer และ UndefinedBehaviorSanitizer แล้วรันการทดสอบทั้งหมด
    - 6.2.2 ตั้งตัวจัดรูปแบบโค้ดและตัววิเคราะห์โค้ดแบบสถิต (static analysis) เช่น clang-format, clang-tidy และ ruff ให้รันทั้งใน CI และในสคริปต์ที่รันก่อน commit (pre-commit hook)
    - 6.2.3 ตั้งกฎป้องกัน branch ให้ pull request ที่ CI ล้มถูกบล็อกจริง แล้วพิสูจน์ด้วย pull request ที่จงใจให้ล้ม
  - **6.3 Docker และคอนเทนเนอร์ (container)** คอนเทนเนอร์คือสภาพแวดล้อมที่แยกออกจากระบบหลักและบรรจุไลบรารีครบ ทำให้ build เดียวกันรันได้บนทุกเครื่อง ใช้มากกับ ROS 2 และการส่งซอฟต์แวร์ขึ้นคอมพิวเตอร์บนหุ่นยนต์
    - 6.3.1 อธิบายความต่างระหว่าง image กับ container และระหว่างคอนเทนเนอร์กับเครื่องเสมือน (virtual machine)
    - 6.3.2 เขียน Dockerfile แบบหลายขั้น (multi-stage) ที่แยกขั้น build ออกจากขั้นรัน ให้ image สุดท้ายเล็กและไม่รันด้วยผู้ใช้ root
    - 6.3.3 จัดลำดับคำสั่งใน Dockerfile ให้ใช้แคชของชั้น (layer cache) ได้ และใช้ `.dockerignore` ไม่ให้ส่งไฟล์ที่ไม่จำเป็น
  - **6.4 คอนเทนเนอร์ในงานพัฒนาหุ่นยนต์** งานจริงต้องให้คอนเทนเนอร์เข้าถึงเครือข่าย อุปกรณ์ USB และหน้าจอ
    - 6.4.1 รันคอนเทนเนอร์ที่เข้าถึงพอร์ตอนุกรมของไมโครคอนโทรลเลอร์ด้วย `--device` และแชร์โฟลเดอร์โค้ดด้วย volume
    - 6.4.2 ใช้ Docker Compose รันหลายบริการพร้อมกัน เช่น ตัวจำลองกับโหนดควบคุม และอธิบายผลของ `network_mode: host`
    - 6.4.3 รัน job ของ CI ภายใน image ของตนเอง และเผยแพร่ image ขึ้น ghcr.io พร้อม tag ที่ตรงกับ release
  - **6.5 การบรรจุและส่งมอบซอฟต์แวร์ (packaging)** คือการทำให้คนอื่นติดตั้งโค้ดได้โดยไม่ต้อง build เอง
    - 6.5.1 บรรจุโค้ด Python เป็นแพ็กเกจด้วย pyproject.toml และระบุรุ่นของไลบรารีที่พึ่งพา
    - 6.5.2 ใช้ workflow ที่สร้าง release และ image อัตโนมัติเมื่อ push tag ใหม่

## แขนง 6 Linux และ command line

> **ข้อสรุปของแขนงนี้:** แขนงนี้ต้องถึงระดับใช้คล่องภายใน 31 มีนาคม 2570 (ปีที่ 1 ไตรมาส 2) ด้วยชั่วโมงรวมประมาณ 60 ชั่วโมง และต้องรักษาระดับไว้ตลอดแผนผ่านการใช้งานทุกวัน สิ่งที่สำคัญที่สุดคือทำงานประจำวันทั้งหมดผ่านบรรทัดคำสั่งตั้งแต่สัปดาห์แรก เพราะแขนง 4 (C++ และ Python) และแขนง 5 (วิศวกรรมซอฟต์แวร์) ยืนอยู่บนแขนงนี้ และหุ่นยนต์เกือบทุกตัวที่ใช้ ROS 2 รันบน Linux

### (ก) หัวข้อหลัก หัวข้อย่อย และหัวข้อย่อยระดับลึก

แขนงนี้ใช้คำศัพท์พื้นฐานต่อไปนี้ เชลล์ (shell) คือโปรแกรมที่รับคำสั่งที่พิมพ์แล้วสั่งระบบปฏิบัติการให้ทำงาน ในแผนนี้หมายถึง Bash เป็นหลัก ส่วนบรรทัดคำสั่ง (command line) คือการทำงานกับคอมพิวเตอร์ด้วยการพิมพ์คำสั่งแทนการคลิกในหน้าจอกราฟิก เทอร์มินัล (terminal) คือหน้าต่างที่แสดงเชลล์ และคู่มือ (man page) คือเอกสารที่มากับคำสั่งแต่ละตัวซึ่งเปิดดูได้ด้วยคำสั่ง `man`

- **1. ไฟล์และสิทธิ์** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 1 ชั่วโมงประมาณ 10)
  - **1.1 ระบบไฟล์และการเคลื่อนที่ (filesystem navigation)** คือโครงสร้างไดเรกทอรีแบบต้นไม้ที่เริ่มจาก `/` ใช้หาไฟล์ตั้งค่า ไฟล์บันทึก และไฟล์อุปกรณ์ของหุ่นยนต์
    - 1.1.1 อธิบายหน้าที่ของ `/etc` `/var/log` `/home` `/tmp` `/dev` `/opt` และ `/usr` จากความจำ และบอกได้ว่าไฟล์ตั้งค่าของบริการหนึ่งน่าจะอยู่ที่ใด
    - 1.1.2 ใช้พาธสัมบูรณ์ (absolute path) และพาธสัมพัทธ์ (relative path) สลับกันได้ถูก และใช้ `cd -` `pushd` และ `popd` ย้ายไปมาระหว่างไดเรกทอรีโดยไม่หลง
    - 1.1.3 ใช้ `ls -la` `stat` `file` และ `tree` อ่านข้อมูลของไฟล์ และแยกไฟล์ปกติ ไดเรกทอรี ลิงก์สัญลักษณ์ (symbolic link) และไฟล์อุปกรณ์ออกจากกันได้
  - **1.2 การจัดการไฟล์ การจับคู่ชื่อไฟล์ด้วยไวลด์การ์ด (glob) และการใส่เครื่องหมายคำพูด (quoting)** เป็นสิ่งที่ทำให้คำสั่งทำงานกับไฟล์จำนวนมากได้ถูกต้องและไม่ลบผิดไฟล์
    - 1.2.1 ใช้ `cp` `mv` `rm` `mkdir -p` และ `ln -s` กับไฟล์หลายร้อยไฟล์ในคำสั่งเดียว โดยใช้ `echo` ตรวจผลของ glob ก่อนรันคำสั่งที่ลบหรือเขียนทับ
    - 1.2.2 อธิบายความต่างระหว่างเครื่องหมายคำพูดเดี่ยว เครื่องหมายคำพูดคู่ และไม่ใส่เครื่องหมาย และทำให้คำสั่งทำงานถูกกับชื่อไฟล์ที่มีช่องว่างหรือขึ้นต้นด้วยขีด
    - 1.2.3 ใช้การขยายวงเล็บปีกกา (brace expansion) และการแทนค่าคำสั่ง (command substitution) สร้างชื่อไฟล์และโฟลเดอร์ตามแบบที่กำหนด
  - **1.3 สิทธิ์ของไฟล์ (file permission) และผู้ใช้** คือกลไกที่บอกว่าใครอ่าน เขียน หรือรันไฟล์ได้ ใช้ควบคุมการเข้าถึงพอร์ตอนุกรมและกล้องของหุ่นยนต์
    - 1.3.1 อ่านสิทธิ์ rwx ทั้งแบบตัวอักษรและแบบเลขฐานแปด และอธิบายสิทธิ์ 755 644 600 และ 2775 จากความจำ
    - 1.3.2 ใช้ `chmod` `chown` `chgrp` และ `umask` ให้สิทธิ์เท่าที่จำเป็น และอธิบายว่าสิทธิ์ x บนไดเรกทอรีหมายถึงอะไร
    - 1.3.3 ตั้งบิต setgid บนไดเรกทอรีกลุ่มให้ไฟล์ใหม่สืบทอดกลุ่ม และอธิบายหน้าที่ของ sticky bit บน `/tmp`
  - **1.4 ผู้ใช้ กลุ่ม และสิทธิ์ผู้ดูแลระบบ** คือการแยกผู้ใช้ทั่วไปกับผู้ใช้ root เพื่อไม่ให้ความผิดพลาดเล็กทำให้ระบบเสียทั้งเครื่อง
    - 1.4.1 ใช้ `id` `groups` `useradd` และ `usermod -aG` เพิ่มผู้ใช้เข้ากลุ่ม `dialout` และ `video` แล้วอธิบายว่าทำไมต้องล็อกอินใหม่
    - 1.4.2 ใช้ `sudo` เฉพาะคำสั่งที่จำเป็น อ่าน `/etc/sudoers` ด้วย `visudo` และอธิบายว่าทำไม `sudo chmod -R 777` เป็นการแก้ปัญหาที่ผิด
- **2. การเปลี่ยนทิศทางและท่อ** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 1 ชั่วโมงประมาณ 12)
  - **2.1 การเปลี่ยนทิศทางข้อมูล (redirection)** คือการส่งผลลัพธ์หรือข้อความผิดพลาดของคำสั่งไปยังไฟล์หรือคำสั่งอื่น ใช้เก็บบันทึกการทดลองของหุ่นยนต์
    - 2.1.1 อธิบายช่องข้อมูลมาตรฐาน stdin stdout และ stderr และเลขอธิบายไฟล์ (file descriptor) 0 1 และ 2 จากความจำ
    - 2.1.2 ใช้ `>` `>>` `2>` `2>&1` และ `/dev/null` แยกผลลัพธ์กับข้อผิดพลาดของคำสั่งลงคนละไฟล์ได้ถูกลำดับ
    - 2.1.3 ใช้ here document และ `tee` เขียนไฟล์ตั้งค่าจากสคริปต์และเก็บผลลัพธ์พร้อมดูบนจอ
  - **2.2 การต่อคำสั่งด้วยท่อ (pipe)** คือการส่งผลลัพธ์ของคำสั่งหนึ่งเป็นข้อมูลเข้าของอีกคำสั่ง ทำให้ตอบคำถามจากข้อมูลจำนวนมากได้ในบรรทัดเดียว
    - 2.2.1 ต่อ `sort` `uniq -c` `wc` `head` `tail` `cut` และ `tr` ตอบคำถามเชิงนับจากไฟล์บันทึกที่มีอย่างน้อย 100,000 บรรทัด
    - 2.2.2 ใช้ `find` ร่วมกับ `xargs` หรือ `-exec` ทำงานกับไฟล์ที่ค้นพบ และจัดการชื่อไฟล์ที่มีช่องว่างด้วย `-print0` กับ `xargs -0`
    - 2.2.3 ใช้ `tail -f` ติดตามไฟล์บันทึกขณะหุ่นยนต์ทำงาน และกรองเฉพาะบรรทัดที่สนใจแบบต่อเนื่อง
  - **2.3 grep กับนิพจน์ปรกติ (regular expression)** คือรูปแบบข้อความที่ใช้ค้นหาบรรทัดที่ตรงเงื่อนไข เช่น ค้นข้อความเตือนจากตัวขับมอเตอร์
    - 2.3.1 เขียนนิพจน์ปรกติแบบพื้นฐานและแบบขยายที่มีกลุ่ม ตัวเลือก และตัวระบุจำนวน และทดสอบกับตัวอย่างที่ควรตรงและไม่ควรตรง
    - 2.3.2 ใช้ `grep -E` `-v` `-c` `-n` `-r` และ `-o` ค้นทั้งโครงการ และรู้ว่าเมื่อใดควรใช้ `rg` แทน
  - **2.4 sed และ awk** คือเครื่องมือแก้ข้อความแบบสายข้อมูล (stream editor) และภาษาประมวลผลข้อความแบบคอลัมน์ ใช้แปลงไฟล์ข้อมูลเซนเซอร์ก่อนวิเคราะห์
    - 2.4.1 ใช้ `sed` แทนที่ข้อความด้วยกลุ่มที่จับได้ ลบบรรทัดตามเงื่อนไข และแก้ไฟล์ในที่เดิมพร้อมเก็บไฟล์สำรอง
    - 2.4.2 ใช้ `awk` เลือกคอลัมน์จากไฟล์ CSV คำนวณค่าเฉลี่ย ค่าสูงสุด และนับตามกลุ่ม แล้วเทียบผลกับสคริปต์ Python อ้างอิง
    - 2.4.3 ตัดสินใจได้ว่างานใดควรจบด้วยคำสั่งบรรทัดเดียว และงานใดควรย้ายไปเขียนเป็นสคริปต์ Python เพราะซับซ้อนเกินจะดูแลได้
- **3. โปรเซสและการตรวจสอบระบบ** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 2 ชั่วโมงประมาณ 9)
  - **3.1 โปรเซส (process) และงานของเชลล์** โปรเซสคือโปรแกรมที่กำลังทำงาน หุ่นยนต์หนึ่งตัวมีโปรเซสพร้อมกันหลายสิบตัว
    - 3.1.1 ใช้ `ps aux` `pgrep` `pstree` และ `htop` หาโปรเซสตามชื่อ ผู้ใช้ และการใช้ CPU และอธิบายคอลัมน์ PID PPID STAT และ RSS
    - 3.1.2 ใช้ `&` `jobs` `fg` `bg` `nohup` และ Ctrl-Z จัดการงานที่รันนาน และอธิบายว่าทำไมโปรเซสลูกตายเมื่อปิดเทอร์มินัล
  - **3.2 สัญญาณ (signal)** คือข้อความสั้นที่ระบบปฏิบัติการส่งถึงโปรเซส ใช้สั่งหยุดโปรแกรมควบคุมหุ่นยนต์อย่างเป็นระเบียบ
    - 3.2.1 อธิบาย SIGINT SIGTERM SIGKILL SIGHUP และ SIGSTOP และเหตุผลที่ต้องส่ง SIGTERM ก่อน SIGKILL เพื่อให้โปรแกรมปิดมอเตอร์และบันทึกข้อมูลก่อนจบ
    - 3.2.2 ใช้ `kill` `pkill` และ `timeout` หยุดโปรเซสที่ค้าง และอ่านรหัสสถานะการจบ (exit status) ที่ได้จากการถูกสัญญาณหยุด
  - **3.3 บริการด้วย systemd และไฟล์บันทึกด้วย journalctl** systemd คือตัวจัดการบริการที่เริ่มและดูแลโปรแกรมเบื้องหลังของ Ubuntu
    - 3.3.1 ใช้ `systemctl status` `start` `stop` `enable` และ `restart` และอ่านสาเหตุที่บริการล้มเหลวจากผลลัพธ์
    - 3.3.2 ใช้ `journalctl -u` `-f` `--since` และ `-p err` หาข้อความผิดพลาดของบริการในช่วงเวลาที่กำหนด
  - **3.4 ทรัพยากรของระบบ** คือ CPU หน่วยความจำ ดิสก์ และพอร์ตเครือข่าย ซึ่งบนคอมพิวเตอร์ของหุ่นยนต์มีจำกัดกว่าบนเครื่องตั้งโต๊ะมาก
    - 3.4.1 ใช้ `df -h` `du -sh` และ `ncdu` หาไดเรกทอรีที่กินดิสก์ และใช้ `free -h` อ่านหน่วยความจำที่ใช้จริงกับแคช
    - 3.4.2 ใช้ `lsof` และ `ss -tlnp` หาโปรเซสที่ยึดไฟล์หรือพอร์ต เช่น พอร์ต 8080
    - 3.4.3 ใช้ `uptime` อ่านภาระเฉลี่ย (load average) และอธิบายว่าค่าเท่าไรถือว่าหนักเมื่อเทียบกับจำนวนแกนของ CPU
- **4. แพ็กเกจ สภาพแวดล้อม และ shell script** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 2 ชั่วโมงประมาณ 14)
  - **4.1 การจัดการแพ็กเกจ (package management)** คือการติดตั้ง ปรับรุ่น และถอนซอฟต์แวร์ผ่านคลังแพ็กเกจ ซึ่งเป็นวิธีที่ ROS 2 ติดตั้งบน Ubuntu
    - 4.1.1 ใช้ `apt update` `apt install` `apt remove` `apt-cache policy` และ `dpkg -L` ตรวจว่าแพ็กเกจติดตั้งไฟล์ไว้ที่ใดและมาจากคลังใด
    - 4.1.2 เพิ่มคลังแพ็กเกจภายนอกพร้อมกุญแจลงนาม (signing key) ได้ถูกวิธี และอธิบายความเสี่ยงของการรันสคริปต์ติดตั้งจากอินเทอร์เน็ตโดยไม่อ่าน
  - **4.2 ตัวแปรสภาพแวดล้อม (environment variable) และไฟล์ตั้งค่าของเชลล์** คือค่าที่โปรแกรมอ่านตอนเริ่มทำงาน เช่น `PATH` และตัวแปรที่ ROS 2 ต้องใช้
    - 4.2.1 อธิบายความต่างระหว่างตัวแปรของเชลล์กับตัวแปรที่ `export` แล้ว และหาว่าคำสั่งหนึ่งถูกเรียกจากไฟล์ใดด้วย `type` และ `which`
    - 4.2.2 อธิบายว่า `.bashrc` และ `.profile` ถูกอ่านเมื่อใด และใช้ `source` โหลดค่าใหม่โดยไม่เปิดเทอร์มินัลใหม่
    - 4.2.3 จัดไฟล์ตั้งค่าส่วนตัว (dotfiles) ใน repository เดียวพร้อมสคริปต์ติดตั้งที่รันซ้ำได้โดยไม่เพิ่มบรรทัดซ้ำ
  - **4.3 โครงสร้างของ shell script** คือไฟล์ที่รวมคำสั่งเชลล์ให้รันซ้ำได้ ใช้ทำงานติดตั้ง สำรองข้อมูล และเตรียมการทดลอง
    - 4.3.1 เขียนตัวแปร เงื่อนไข `if` และ `case` การวนซ้ำ `for` และ `while` ฟังก์ชัน และอาร์เรย์ของ Bash ได้โดยไม่เปิดเอกสาร
    - 4.3.2 อ่านอาร์กิวเมนต์ด้วยพารามิเตอร์ตำแหน่ง (positional parameter) และ `getopts` พร้อมข้อความวิธีใช้เมื่อใส่ตัวเลือกผิด
    - 4.3.3 ใช้รหัสสถานะการจบ `&&` และ `||` ควบคุมลำดับงาน และคืนรหัสที่มีความหมายให้โปรแกรมที่เรียก
  - **4.4 การจัดการข้อผิดพลาดและการตรวจคุณภาพสคริปต์** คือสิ่งที่ทำให้สคริปต์หยุดอย่างปลอดภัยเมื่อมีขั้นตอนใดล้มเหลว แทนที่จะทำต่อจนเสียหาย
    - 4.4.1 อธิบายผลของ `set -euo pipefail` ทีละตัว และกรณีที่ `set -e` ไม่หยุดสคริปต์ตามที่คาด
    - 4.4.2 ใช้ `trap` ลบไฟล์ชั่วคราวและคืนสภาพเมื่อสคริปต์จบหรือถูกกด Ctrl-C
    - 4.4.3 ใช้ shellcheck ตรวจสคริปต์จนไม่มีคำเตือน และเขียนการทดสอบอัตโนมัติด้วย bats อย่างน้อย 8 กรณีต่อสคริปต์
  - **4.5 การตั้งเวลางาน (scheduling)** ใช้รันงานซ้ำตามเวลา เช่น สำรองข้อมูลการทดลองทุกคืน
    - 4.5.1 เขียนบรรทัด `crontab` ตามเวลาที่กำหนดได้ถูก และส่งผลลัพธ์ของงานไปเก็บในไฟล์บันทึก
    - 4.5.2 อธิบายว่าทำไมงานที่รันได้ในเทอร์มินัลแต่ล้มเหลวใน cron มักเกิดจาก `PATH` และไดเรกทอรีทำงาน
- **5. SSH และเครื่องระยะไกล** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 2 ชั่วโมงประมาณ 10)
  - **5.1 SSH และการยืนยันตัวตนด้วยกุญแจ** SSH (secure shell) คือโปรโตคอลที่ใช้ล็อกอินเข้าเครื่องอื่นอย่างปลอดภัย ใช้เข้าคอมพิวเตอร์บนหุ่นยนต์ที่ไม่มีจอ
    - 5.1.1 สร้างกุญแจแบบ ed25519 ด้วย `ssh-keygen` ติดตั้งด้วย `ssh-copy-id` และอธิบายว่ากุญแจลับต้องมีสิทธิ์ 600
    - 5.1.2 ตั้ง `~/.ssh/config` ให้ล็อกอินด้วยชื่อย่อ และปิดการล็อกอินด้วยรหัสผ่านใน `sshd_config` แล้วทดสอบว่าถูกปฏิเสธจริง
    - 5.1.3 อธิบายข้อความเตือนเมื่อกุญแจของเครื่องปลายทาง (host key) เปลี่ยน และรู้ว่าเมื่อใดต้องหยุดถามผู้ดูแลก่อนลบออกจาก `known_hosts`
  - **5.2 การคัดลอกและซิงก์ไฟล์** ใช้ส่งโค้ดเข้าหุ่นยนต์และดึงไฟล์บันทึกออกมาวิเคราะห์
    - 5.2.1 ใช้ `scp` และ `rsync -avz --delete` ซิงก์ไดเรกทอรี และใช้ `--dry-run` ตรวจก่อนลบไฟล์ปลายทาง
    - 5.2.2 ใช้ `rsync` แบบไม่ส่งไฟล์ที่ไม่จำเป็นด้วย `--exclude` เช่น ไดเรกทอรีผลการคอมไพล์
  - **5.3 การส่งต่อพอร์ต (port forwarding) และการเข้าถึงผ่านเครื่องกลาง** ใช้เปิดหน้าเว็บหรือเครื่องมือแสดงผลที่รันบนหุ่นยนต์จากเครื่องของตัวเอง
    - 5.3.1 ใช้ `ssh -L` ส่งต่อพอร์ตจากเครื่องระยะไกลมายังเครื่องตัวเอง และอธิบายความต่างกับ `ssh -R`
    - 5.3.2 ใช้ `ProxyJump` เข้าเครื่องที่อยู่หลังเครื่องกลาง และรันคำสั่งเดียวบนเครื่องปลายทางโดยไม่เปิดเชลล์ค้าง
  - **5.4 tmux และการทำงานที่ไม่หลุดเมื่อการเชื่อมต่อขาด** tmux คือโปรแกรมแบ่งหน้าจอเทอร์มินัล (terminal multiplexer) ที่ทำให้งานยังรันต่อเมื่อ SSH หลุด
    - 5.4.1 สร้าง ออก และกลับเข้าเซสชัน แบ่งหน้าต่าง และเลื่อนดูผลลัพธ์ย้อนหลังโดยไม่ใช้เมาส์
    - 5.4.2 รันการทดลองยาวใน tmux บนเครื่องระยะไกล แล้วตัดการเชื่อมต่อและกลับมาดูผลได้ครบ
  - **5.5 เครือข่ายพื้นฐานจากบรรทัดคำสั่ง** ใช้วินิจฉัยว่าหุ่นยนต์กับเครื่องควบคุมคุยกันไม่ได้เพราะอะไร
    - 5.5.1 ใช้ `ip addr` `ip route` `ping` และ `nc` ตรวจที่อยู่ เส้นทาง และพอร์ตปลายทาง
    - 5.5.2 ใช้ `curl` และ `dig` ทดสอบบริการเว็บและการแปลงชื่อเครื่อง และแยกได้ว่าปัญหาอยู่ที่ชื่อ ที่เส้นทาง หรือที่ไฟร์วอลล์
- **6. Linux สำหรับคอมพิวเตอร์บนหุ่นยนต์: อุปกรณ์ บริการ และ container** (ระดับเป้าหมาย: ใช้คล่อง ภายในปีที่ 1 ไตรมาส 2 ชั่วโมงประมาณ 5)
  - **6.1 ไฟล์อุปกรณ์และพอร์ตอนุกรม (serial port)** คือการติดต่อไมโครคอนโทรลเลอร์ เซนเซอร์ และกล้องผ่านไฟล์ใน `/dev`
    - 6.1.1 ใช้ `dmesg -w` `lsusb` และ `ls -l /dev/ttyACM*` หาว่าอุปกรณ์ที่เพิ่งเสียบได้ชื่ออะไร และแก้ปัญหาสิทธิ์ด้วยกลุ่ม `dialout` แทน `sudo`
    - 6.1.2 เขียนกฎ udev (udev rule) ให้อุปกรณ์ได้ชื่อคงที่ตามหมายเลขประจำเครื่อง ไม่เปลี่ยนตามลำดับการเสียบ
  - **6.2 เขียนบริการ systemd ของตัวเอง** ใช้ให้โปรแกรมของหุ่นยนต์เริ่มเองเมื่อเปิดเครื่องและเริ่มใหม่เมื่อล้ม
    - 6.2.1 เขียนไฟล์ `.service` ที่รันในชื่อผู้ใช้ทั่วไป กำหนด `Restart=on-failure` และลำดับการเริ่มหลังเครือข่ายพร้อม
    - 6.2.2 ทดสอบโดยฆ่าโปรเซสแล้วยืนยันจาก journalctl ว่าบริการเริ่มใหม่ภายในเวลาที่ตั้งไว้
  - **6.3 container สำหรับสภาพแวดล้อมที่ทำซ้ำได้** container คือการแยกโปรแกรมพร้อมไลบรารีที่ต้องใช้ให้รันเหมือนกันทุกเครื่อง ซึ่งเป็นวิธีที่ทีมหุ่นยนต์จำนวนมากใช้แจกจ่ายสภาพแวดล้อม ROS 2
    - 6.3.1 ใช้ `docker run` `docker exec` และการเชื่อมไดเรกทอรี (bind mount) ทดสอบสคริปต์ใน container ubuntu ใหม่
    - 6.3.2 เขียน Dockerfile ที่ติดตั้งแพ็กเกจและ dotfiles แล้วให้ระบบทดสอบอัตโนมัติ (continuous integration, CI) รัน setup.sh ใน container นั้นทุกครั้งที่ส่งโค้ด
    - 6.3.3 อธิบายว่าการส่งอุปกรณ์ USB และหน้าจอกราฟิกเข้า container ต้องใช้ตัวเลือกใด และความเสี่ยงของ `--privileged`

**เหตุผลของลำดับ:** หัวข้อ 1 มาก่อนเพราะทุกคำสั่งในหัวข้อถัดไปทำงานกับไฟล์และพาธ และความผิดพลาดเรื่อง quoting กับสิทธิ์เป็นต้นเหตุของปัญหาส่วนใหญ่ที่ผู้เริ่มต้นเจอ หัวข้อ 2 ต่อจากหัวข้อ 1 ทันทีเพราะท่อและการเปลี่ยนทิศทางเป็นแนวคิดที่ทำให้บรรทัดคำสั่งเหนือกว่าหน้าจอกราฟิก และเป็นเครื่องมือหลักในการอ่านไฟล์บันทึกของหุ่นยนต์ หัวข้อ 3 ตามมาเพราะต้องเข้าใจไฟล์และท่อก่อนจึงจะอ่านผลของ `ps` `lsof` และ `journalctl` ได้ หัวข้อ 4 รวมทุกอย่างก่อนหน้าเข้าเป็นสคริปต์ จึงต้องอยู่หลังหัวข้อ 1 ถึง 3 ตามหลักการเรียนจากส่วนย่อยไปสู่การประกอบ หัวข้อ 5 วางหลังหัวข้อ 4 เพราะการตั้งเครื่องระยะไกลต้องใช้ทั้งสิทธิ์ไฟล์ บริการ และสคริปต์ และสอดคล้องกับลำดับของ Bandit ที่ด่าน 13 ถึง 24 ต้องใช้ความรู้ด้านเครือข่ายและโปรเซส หัวข้อ 6 อยู่ท้ายสุดเพราะเป็นการประยุกต์หัวข้อ 1 ถึง 5 กับคอมพิวเตอร์บนหุ่นยนต์โดยตรง ผมเพิ่มหัวข้อนี้จากภาคผนวกเพราะวิศวกรหุ่นยนต์ต้องทำให้ไมโครคอนโทรลเลอร์ กล้อง และโปรแกรมควบคุมทำงานเองเมื่อเปิดเครื่องได้ และต้องแจกจ่ายสภาพแวดล้อมที่ทำซ้ำได้ (ความเห็น ความมั่นใจปานกลางถึงสูง) การเรียนแต่ละหัวข้อสลับกับการเล่น Bandit และการใช้งานจริงทุกวัน เพราะการฝึกดึงความจำ (retrieval practice) และการเว้นระยะ (spacing) ให้ความคงทนดีกว่าการอ่านรวดเดียว (ข้อเท็จจริงจากงานวิจัยการเรียนรู้ที่ตอนที่ 1 ข้อ 1.5 อ้างไว้ ความมั่นใจสูง) ชั่วโมงรวมของหัวข้อ 1 ถึง 6 คือ 10 บวก 12 บวก 9 บวก 14 บวก 10 บวก 5 เท่ากับ 60 ชั่วโมงตรงกับตาราง 2.2 แขนงนี้มีความยาวเท่าแขนงทั่วไปเพราะไม่ใช่แกนลึก

**เหตุผลของความลึกเป้าหมาย:** ตาราง 2.2 ของตอนที่ 1 กำหนดแขนงนี้ไว้ที่ใช้คล่อง 60 ชั่วโมง เริ่มและจบในปีที่ 1 (ข้อเท็จจริงของเอกสารนี้ ความมั่นใจสูง) ผมวางเส้นตายใช้คล่องไว้ที่ 31 มีนาคม 2570 แทนสิ้นปีที่ 1 เพราะแขนง 18 (ROS 2 และ simulation) เริ่มในปีที่ 1 ไตรมาส 4 และต้องใช้ apt ตัวแปรสภาพแวดล้อม SSH และ container ได้ก่อนเริ่ม ถ้าเลื่อนไปจบพร้อมแขนง 18 เวลาของไตรมาสนั้นจะหมดไปกับการแก้ปัญหาของระบบปฏิบัติการแทนการเรียน ROS 2 (อนุมาน ความมั่นใจปานกลาง) ระดับที่สูงกว่านี้ เช่น การเขียนโมดูลเคอร์เนล (kernel module) การปรับเคอร์เนลแบบเวลาจริง (PREEMPT_RT) หรือการดูแลเครื่องแม่ข่ายระดับองค์กร ไม่คุ้มสำหรับเป้าหมายวิศวกรหุ่นยนต์ เพราะเป็นงานของวิศวกรระบบหรือวิศวกรเฟิร์มแวร์เฉพาะทาง และหัวข้อที่เกี่ยวกับเวลาจริงที่หุ่นยนต์ต้องใช้จะเรียนในแขนง 3 (ระบบปฏิบัติการและ concurrency ในปีที่ 2 ไตรมาส 1) และแขนง 21 แทน (ความเห็น ความมั่นใจปานกลาง) ในทางกลับกัน ระดับรู้พอใช้ไม่พอ เพราะวิศวกรหุ่นยนต์ต้องวินิจฉัยปัญหาที่ไม่เคยเห็นบนเครื่องที่ไม่มีจอ ผ่าน SSH ภายใต้แรงกดดันของการทดลอง ซึ่งการเปิดเอกสารทุกคำสั่งทำไม่ทัน (ความเห็น ความมั่นใจปานกลางถึงสูง) ผมบอกตรง ๆ ว่า 60 ชั่วโมงพอถึงใช้คล่องได้ก็ต่อเมื่อใช้บรรทัดคำสั่งในงานของแขนงอื่นทุกวันด้วย ถ้าเรียนเฉพาะ 60 ชั่วโมงนี้แล้วกลับไปใช้หน้าจอกราฟิก ความคล่องจะหายภายในไม่กี่เดือน (อนุมาน ความมั่นใจปานกลาง)

**ผลแบบทดสอบวัดระดับ (ส่วนที่ 5) จะเปลี่ยนตารางนี้อย่างไร:** ผมไม่เดาระดับเริ่มต้น และใช้กติกาต่อไปนี้แทน ถ้าเล่น Bandit Level 0 ถึง 10 ได้รวดเดียวภายใน 1 ชั่วโมงโดยไม่ดูคำใบ้ ให้ข้าม TLCL Part 1 ตามภาคผนวก ลดหัวข้อ 1 และ 2 เหลือเฉพาะงานทดสอบในข้อ (ง) และย้ายชั่วโมงที่เหลือประมาณ 15 ชั่วโมงไปให้แขนง 4 ถ้าทำงานทดสอบปิดแขนงฉบับย่อในแบบทดสอบวัดระดับได้อย่างน้อย 11 จาก 12 ข้อ ให้ถือว่าแขนงนี้ถึงใช้คล่องแล้ว เหลือเพียงด่าน 5 และด่าน 6 และย้ายชั่วโมงเกือบทั้งหมดไปที่แขนง 4 และ 5 ถ้าผ่าน Bandit ได้ไม่ถึง Level 5 ใน 1 ชั่วโมง ให้ใช้ตารางนี้ตามเดิมโดยไม่เลื่อนเส้นตาย เพราะ 60 ชั่วโมงคำนวณจากการเริ่มที่ศูนย์อยู่แล้ว ถ้าเส้นตาย 31 ธันวาคม 2569 พลาด ให้ตัดเวลาของสายเครื่องมือในส่วนอื่นก่อน ห้ามเลื่อนเส้นตาย 31 มีนาคม 2570 เพราะแขนง 18 รออยู่

## ข้อจำกัดของตอนนี้และสิ่งที่ควรศึกษาต่อ

### ข้อจำกัด

1. ผมตรวจทุกแขนงในตอนนี้ด้วยสคริปต์อัตโนมัติ ได้แก่ โครงสร้างหัวข้อ จำนวนหัวข้อ ชั่วโมงรวม ความเชื่อมโยงกับแผนผัง ความยาว และสัญลักษณ์ต้องห้าม แต่ยังไม่ได้อ่านทวนเนื้อหาเชิงเทคนิคทุกบรรทัด เพราะโควตาการใช้งานของรอบนี้จำกัด ถ้าพบหัวข้อที่ผิดหรือลำดับที่ไม่สมเหตุสมผล ให้แจ้งเพื่อแก้
2. สถานะของแหล่งเรียนมาจากการตรวจเมื่อ 3 ตุลาคม 2569 ในรอบภาคผนวก ข้อมูลส่วนใหญ่มีสถานะ "ยืนยันจากผลค้นหา" เพราะหลายโดเมนถูกบล็อก และเลขบทบางบทที่เพิ่มในตอนนี้ยังไม่ยืนยัน
3. ชั่วโมงต่อหัวข้อเป็นการประมาณของผม (อนุมาน ความมั่นใจต่ำถึงปานกลาง) ชั่วโมงจริงจะเปลี่ยนตามผลแบบทดสอบวัดระดับ
4. เลขบทของ The Missing Semester ฉบับปี ค.ศ. 2026 และของ The Linux Command Line บางบทยังไม่ยืนยัน ต้องตรวจเมื่อเปิดแหล่งจริง

### สิ่งที่ควรศึกษาต่อ

1. หลังทำแบบทดสอบวัดระดับในตอนที่ 9 ให้แก้ตารางในหัวข้อ (ข) ของทุกแขนงตามผลสอบ และบันทึกลง learning-log
2. เมื่อเปิดแหล่งเรียนจริง ให้ตรวจเลขบทที่ระบุว่ายังไม่ยืนยัน แล้วแก้ตารางแผนที่บทในหัวข้อ (จ)
3. หลังเรียนแต่ละหัวข้อหลักครบ ให้เทียบชั่วโมงจริงกับชั่วโมงที่ประมาณไว้ ถ้าต่างเกินร้อยละ 30 ให้ปรับหัวข้อถัดไปของแขนงเดียวกัน
4. หลังใช้ Git และ Linux ทุกวันครบ 4 สัปดาห์ ให้ทำด่าน 5 ของแขนง 5 และ 6 เพื่อตรวจว่าการใช้ทุกวันพอทดแทนชั่วโมงเรียนที่ตั้งไว้หรือไม่
